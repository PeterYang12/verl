# DSV4 RL-Kernel / verl integration

This opt-in entrypoint runs verl's synchronous v1 trainer with its native GRPO
reward, advantage and PPO policy loss. RLK supplies the native MCore operator
bindings, selected FP32 logprob provider, original packed checkpoint loading and
checked synchronization to a live standalone vLLM PP2 replica.

It consumes actual forward logits at the provider boundary, following the
integration pattern in [Vime #424](https://github.com/vllm-project/vime/pull/424).
It does not replace the trainer with the four-layer diagnostic loss or an
independent training engine.

The existing image also needs its matching Bridge/AITER/Torch/ROCm dependencies.
Record the actual installed commits, local patches, package versions and image
digest before accepting a result. The original four-layer checkpoint and scales
must be identical on both sides. Packed FP4/FP8 bases remain frozen; the native
optimizer updates the supported nonquantized parameters and retains input VJPs
through the packed experts. This is not full-parameter quantized-weight training.

## Four-card topology

- Actor: PP2, DP1, TP1, EP1, CP1, two GPUs.
- Rollout: a separate native vLLM PP2 replica, two other GPUs.
- Both engines own original checkpoint layers `0–2 / 3`.
- Eager mode, no LoRA, MTP, reference/KL, critic, sleep, prefix caching or resume.
- Unit temperature, full vocabulary scores, no top-k/top-p truncation.
- GRPO uses at least two completions per prompt. The mini-batch setting counts
  prompts; equal `data.train_batch_size` and `actor.ppo_mini_batch_size` with one
  PPO epoch yield one real optimizer update per global step.

## Entry

Install the community verl branch and RLK #711 in the isolated runtime, keeping
the previously measured MCore/vLLM dependencies. Do not install a second upstream
verl over this fork. Run only after the selected four GPUs are actually free;
restrict device visibility and Ray GPU resources before launching this command.

```bash
python -m verl.experimental.rl_kernel.main_ppo \
  actor_rollout_ref.model.path=/models/4l \
  data.train_files=/data/train.parquet \
  data.val_files=/data/val.parquet \
  data.train_batch_size=2 \
  actor_rollout_ref.actor.ppo_mini_batch_size=2 \
  actor_rollout_ref.rollout.n=2 \
  trainer.total_training_steps=3 \
  trainer.default_local_dir=/outputs/checkpoints \
  rlk.sync_dir=/outputs/policy-sync
```

These are explicit mount paths, not bundled model/data assets. Use a real
supported rule-reward dataset, or its documented custom reward implementation.
Check that group rewards and advantages actually differ; zero advantages and
unchanged weights cannot qualify as three effective training updates.

## What the adapter records

- `parity.jsonl`: actor old-logprob versus actual rollout scores from the native
  TransferQueue batch, compared as finite FP32 bits on response positions.
- `training-batch-step{1,2,3}.json`: actual native reward/return/advantage summaries.
- `actor-rank-*-identity.json`: live actor PIDs, device identities and layer ownership.
- `actor-rank-*-v{1,2,3}.json`: native optimizer versions, finite/nonzero gradient
  evidence and parameter changes on both actor stages.
- `sync-v{0,1,2,3}.json`: complete original-tensor readback on both live rollout
  stages. Version zero verifies the shared initial checkpoint; it is not an update.
- `post-update-v{1,2,3}.json`: new tokens generated by the live updated rollout
  and scored by the same live actor. This also verifies the final update.

Sync closes admissions and clears caches before export. A missing shard, stale
version, changed worker PID, incomplete readback, nonfinite score or bit mismatch
fails the run. Ordinary non-RLK entrypoints and registries are unchanged.

## Acceptance status

This branch is integration code awaiting machine-side validation. No GPU test or
complete GRPO acceptance is claimed here. Earlier #711 diagnostic results do not
qualify this new full trainer entrypoint. Run three continuous real updates in
one job, retaining worker PIDs and optimizer state; do not restart version one
three times. Save all logs and failures, confirm a clean exit, and inspect the
evidence above before reporting success.

Also verify actual B1/B2 scheduling, fixed token alignment and AB/BA/repeat batch
invariance on the same weight version. A request list of length two alone does
not prove that the engine executed a two-request batch. Add any runtime fixes to
this existing community-fork branch and RLK #711 as appropriate. Do not submit
changes to upstream verl, Megatron, Bridge, vLLM or AITER, and do not auto-merge.
